**事故：Skill 参数替换破坏 SKILL.md 中的美元数字字面量（2026-07-04 发现并修复）**
- 问题：us-options-agent/SKILL.md 里的账户金额（美元符+数字，如 8,500 / 2,550）在带 args 调用 Skill 时被当成位置参数替换，渲染成 "PLTR,500" 之类乱码

- 修复：SKILL.md 中一律不写"美元符+数字"；具体金额改由 memory/state/options-journal.md 维护，SKILL.md 只写百分比规则（5%/30%）
- 教训：**SKILL.md 是会被参数替换渲染的模板，不是普通 Markdown；金额/含美元符文本要么放 references/（Read 加载不受影响），要么用"美元"后缀写法**

**事故：fetch_research_data.py 从未推到 main，research 工作流全部失败（2026-07-04 发现并修复）**
- 问题：fetch-research-data workflow 每次运行都 failure，research_cache/_manifest.json 长期 404
- 根因：workflow yml 在 main 上，但它调用的 scripts/fetch_research_data.py 只存在于工作分支——Action 只跑 main 上的代码
- 修复：把脚本推上 main（已确认在 main 树中）；本地两个 workflow yml 反向同步 main 的改进版（[skip ci] + pull --rebase）
- ⚠️ 验证未闭环（2026-07-04）：脚本部署后触发了 06862.HK 测试，但 main 上未出现 "chore: update research cache" 提交，research_cache/ 仍不存在——工作流存在第二层故障（需看 Action 运行日志诊断，当时 GitHub 连接断开无法查看）。**下次会话如需 research 缓存：先查 main 是否有 research_cache/，没有则去 GitHub Actions 页面看 fetch-research-data 最新 run 的失败日志再修**
- 教训：**这是 1.1 节"本地脚本必须同步推 main"教训的重演，且更隐蔽——不只是"改了要同步"，是"新增文件也要确认部署"。任何 GitHub Action 依赖的文件，创建后第一件事是验证 main 上存在；且修复后必须等到产物真实出现才算闭环**

### 1.1b 出口 403 的分诊：站点拒绝 vs 出口策略封禁（2026-08-06 确认）

**事故**：SNDK 财报分析 v1 中，六个逐字记录源（sec.gov / investor.sandisk.com / fool.com / alphastreet / benzinga / investing.com）WebFetch 全部返回 403。我把这当成终点，直接把「分析师 Q&A」整节降级为"依据公开报道重构的应问清单"，并在报告里声明为低置信。用户看到未核实项清单后要求「这几个问题给我马上解决」。

**分诊方法（必须先做，再下结论）**：
```
curl -sS "$HTTPS_PROXY/__agentproxy/status"     # 看 recentRelayFailures
curl -sS -o /dev/null -w "%{http_code}" -L <url>  # CONNECT tunnel failed = 代理层
```
- `curl: (56) CONNECT tunnel failed, response 403` → **出口策略封禁**，README 明确要求不得绕行、只能报告被封主机
- 站点返回 403 但 CONNECT 成功 → 站点在挡 UA，换 UA/换源可解

**根因（真正的教训）**：**"这个通道取不到"≠"这个内容取不到"。**
本次改用 **WebSearch**（未被封）配合足够具体的查询，把分析师提问和管理层回答**逐条问了出来**——包括我原以为拿不到的 CEO/CFO 原话。结果推翻了 v1 的两处判断（位元约束是供给不是需求；毛利率微降来自成本不是价格），并发现了 NBM 的价格下限条款，直接导致评级上修。

**规则**：
1. 遇到 403，**先分诊代理层还是站点层**，不要笼统写成"数据源不可得"
2. 被封的是**主机**，不是**信息**。至少要穷尽：WebSearch 定向查询、GitHub Action（无限制出口）、聚合站
3. **禁止把"取数失败"直接转化为报告里的低置信声明**——声明是穷尽通道之后的结果，不是替代穷尽的借口
4. 已知可用通道：**WebSearch、GitHub Action**；已知封禁：sec.gov、investor.sandisk.com、fool.com、alphastreet、benzinga、investing.com、stockanalysis.com

### 1.1d ⭐ 答案前置：客户要结果，不要我的自证过程（2026-08-06 用户投诉，最高优先级）

**用户原话**：「我对你最近客户发来提纲的表现不满意，我要的是结果，你可以在你的推测结果或者分析结果的最后开一个板块说明你的看法，但是在分析和推测撰写的时候，我不满意你的各种精力涣散。」

**问题表现**：海昌 IT 提纲、SNDK 财报等报告的正文里，每隔几句就插入置信度徽章、「本报告未能核实」「公开渠道未见披露，我们尝试从三个角度」「我在 v1 里说错了」等元叙述。读者要在我的认识论里跋涉才能找到答案。

**根因（不是写作习惯，是规则）**：Critic 的 D3 原文要求「每个结论有置信度标注」「低置信结论显式标注，不是藏在正文里」；Merlin 模式B 要求「每条推测标【推测】前缀 + 假设层数 + 结尾重申非公司确认事实」；restaurant-research 要求逐条打来源标签。**我为了过闸门，把严谨性证明写进了正文。改写作没用，必须改规则。**

**已执行的规则修改（2026-08-06）**：
| 文件 | 改动 |
|------|------|
| `critic/SKILL.md` | D3 增加**反向检查**（元叙述散文 / 单段≥2徽章 / 元内容占篇幅1/3 → flag）；新增 **D3b 答案前置硬检查**；REWRITE 触发条件增加两条 |
| `critic/references/skill-checklists.md` | 通用检查新增「答案前置」四条，含 REWRITE 级 |
| `merlin/SKILL.md` | 输出规范重写；模式B必含项改为"每条第一句即结论"；新增**答案前置原则**章节（含正反例） |
| `restaurant-research-skill/SKILL.md` | 核心原则2/4 补注；新增**答案前置原则**章节 |
| `earner/SKILL.md` | 新增**答案前置原则**章节；版本修订说明只写附注不写正文 |

**统一架构（所有报告类型适用）**：
| 位置 | 只放 | 绝不放 |
|------|------|--------|
| **正文** | 结论、数字、支撑推理链条、区间 | 数据来源限制、方法说明、假设层数、自我更正、"未能核实"类元叙述 |
| **末尾「分析师附注 / Analyst's Note」** | 置信度总表、数据缺口与推测依据、方法与来源限制、**分析师独立看法与分歧点**、待核实项 | — |

**写法**（客户提纲逐条回答）：
```
✅ 答：约 1.2-1.5 亿元，占营收 3.5%。依据：2023年公告的三年规划总投入 4.5 亿、
      按行业惯例首年 30% 投放推算；同期可比项目 3.2%-3.8%。 [中置信]
❌ 答：这个问题公开渠道未见直接披露。我们尝试从三个角度推断，但需要说明的是……
```

**三条可操作判据**：
1. **第一句必须是结论本身**（数字或判断），不是「关于X这个问题……」
2. **用区间表达不确定性，不用「可能」「大致」**——软化词是偷懒，区间才是信息
3. **删掉正文里所有讲"我怎么知道的"的句子，答案还完整吗？** 不完整=推理没写够；更清爽=那些句子本来就该在附注里

**注意**：严谨性本身不打折——置信度、数据缺口、推测依据一条都不少，只是**换个位置**。**这是搬家，不是删除。**

### 1.1e ⭐ 标尺必须含「张数」——止损口径与跳空亏损是两回事（2026-08-06）

**事件**：我建议 UBER $62.50 Put Sep18 × **1 张**；用户实际成交 $62 Put Sep11 × **6 张** @ $0.50。
交易本身赔率优于我的推荐（实价反解 IV 35.1%、PoP 85.1%、缓冲 11.02%、单张 Δ 仅 −0.125、财报窗口干净）。
**但接货义务 = $62×100×6 = $37,200 = 净值 392%，保证金 $3,754 使组合保证金达净值 48%（上限 30%）。**

**根因：我前一天刚立的三把尺子，有两把放行了这笔。**
| 尺子 | 判定 |
|---|---|
| 权利金 ≤ $2.35/股 | $0.50 → ✅ 通过 |
| 止损口径 ≤ 净值 5% | 2×$300 = $300 = 3.2% → ✅ 通过 |
| 接货市值 ≤ 可取现金 | $37,200 vs $7,800 → ❌ 超 4.8 倍 |

**全部标尺都按「单张」定义，没有一条约束张数。**

**⭐ 核心认识（可迁移到任何仓位管理场景）**：
**六张 $0.50 的合约与一张 $3.00 的合约，止损口径的钱完全相同（都是 $300），但标的跌破行权价后，前者的亏损斜率是后者的六倍。**
- **R1/R2（权利金、止损口径）度量的是「纪律生效时」的损失**
- **R3/R5/R6（接货义务、张数、组合Delta）度量的是「纪律来不及生效时」的损失**
- **小账户真正会被打死的是后者。** 跳空不给你执行止损的机会。

**已补的标尺（详见 `memory/state/options-journal.md` 标尺体系 v3）**：
- R3 改为 **接货市值 = 行权价 × 100 × 张数**（原文隐含单张）
- 新增 R5 **单标的张数上限**（由接货义务 ≤ 净值×1.5 反推）
- 新增 R6 **组合 Delta 美元敞口 ≤ 净值 1%/美元**（标的每跌 $1 的总亏损）

**规则：每次给开仓建议时，必须显式写出张数，并同时给出「若加倍/加到N张会怎样」的接货义务与跳空亏损表**，不能只报单张数字让用户自己乘。

### 1.3b 换壳 vs 重做（2026-07-21 确认）

**问题：用错 skill/流程后，只做"表面合规"修正，被用户识破**
- 场景：绿茶×海底捞访谈提纲首版误用 restaurant-research，发现后只是把文件名/反馈链接改成 Merlin 格式、补了三个必需区块（流程图/风险表/裁定区块），但内容本身没有真正走 Merlin 五智能体流程（Scout未实际检索、Analyst/Forensic未真推理）
- 用户原话："我觉得重新来一遍会比较好，修改的过于应付"
- 根因：**格式合规 ≠ 流程真实性**。给报告"换壳"（改标题、补区块结构）能过 Critic 的格式检查，但内容还是原来那套，没有对应流程本该产生的增量信息
- 正确模式：**发现用错 skill/流程后，先判断问题性质——是"外壳/命名/格式错了"还是"根本没走对应的取证/推理步骤"。前者才能补丁式修正；后者必须真正重跑对应流程（如 Merlin 模式B 就要真派 Scout 检索、真让 Analyst/Forensic 推理），产出应该有实质性新增量（新数据/新纠正/新洞察），而不是给旧内容套新模板**
- 验收标准：重做后应该能列出"相比上一版的实质性差异"，如果只有格式/命名变了、内容一字未变，说明还是在换壳

### 1.4 CSS/布局错误

**问题：Merlin critic-box 白屏（只有几个字，大量留白）**
- 根因：外层 `div` 同时带了 `critic-box`（边框）和 `critic-header`（display:flex），两 class 叠加后内容横向并列被 overflow:hidden 截断
- 修复原则：**每个 CSS class 单一职责，容器 class 不做 flex 布局，布局 class 不加 overflow**
- 教训：HTML 生成前必须检查 class 叠用

### 2.2 UI 设计偏好

- 字体：IM Fell English（英文衬线）+ Songti SC（中文衬线）

### 2.4 数据处理理念

**数据诚实优先**
- 每个关键数字注明来源和日期：`【一手·财报】` / `【二手·媒体】` / `【推断】` / `【分析预测】`
- 多源数据冲突时：一手 > 二手；差异 ≤15% 取均值；>15% 并列呈现

**数据缺口默认走推测，不留空（2026-07-03 确认，见 R-D6）**
- 用户原话："优化一下这个流程，对于没有信源造成空白的问题，用信息拼接推测+实际市场调研结果进行有效预测，不要空着"
- 找不到直接数据 ≠ 报告可以留白——必须先做**信息拼接推测**（把碎片化真实信息组合成推理链条：锚点数据→显式假设→结论）+ **市场调研交叉验证**（行业基准/可比公司数据侧向校准范围），产出具体推测结论
- 只有维度**结构性不存在**时（如财报体系本身不按此维度披露），才允许保留纯`【数据缺口】`，且要说明"为什么是结构性问题"+ 尽量给侧向代理数据
- 推测结论必须标【推测】/【预测】+ 假设层数（1层 vs 3-4层，层数越多置信度越低）+ 结尾重申"非确认事实"，不给假精确单点数字，给区间
- 已固化进 3 处 skill 文件：`merlin/SKILL.md`（新增"数据缺口处理原则"）、`restaurant-research-skill/references/industry-benchmarks.md`（新增"方法四：信息拼接组合推理法"）、`critic/SKILL.md` + `skill-checklists.md`（D3 新增缺口留白检查，3+处无推测替代触发 REWRITE）
- 实战范式参考：绿茶集团品类采购定量模型（酒水占比×自制占比×品类权重）、海底捞6个内部机制问题推理（COO职责/爬坡周期/薪酬考核）、海底捞2026年6月运营数据推算模型（H1/H2隐含拆分+季节性假设+线性外推）

### 1.1g R7 的适用边界：开仓用实际波动，估值必须用平台实价（2026-08-19 补）

**R7 原文**（2026-08-12 因 INTC 权利金低估 179% 而设）：IV 下限必须由标的自身实际波动倒推，与行业常规取大。
**这条只适用于「开仓定价」**——你在为**未来**波动收钱，不能低估。

**8/19 发现它在另一个方向同样会错**：给**已有仓位估值**时，实际波动是**后视的**，大跌后必然高估。
- INTC 两天跌 9%，我按「大跌后 IV 抬升」推到 78%，真实 IV 只有 **63.4%**
- 该标的近三日实际波动年化 **70.5%，仍高于真实 IV** —— 市场认为这波波动不会持续
- 结果：估值高估 44%，我把平仓成本从 $140 说成了 $402，**夸大 $262**

**两个方向的错误成因相同：都是拿历史波动当未来波动。**

**规则**：
| 场景 | 用什么 |
|---|---|
| 开仓定价、判断权利金够不够 | R7：max(标的近期实际波动, 行业常规) |
| **给已有仓位估值、任何止盈止损决策** | **平台实价，不得用任何模型** |
| 无平台实价时的方向性判断 | 可用 BS，但**必须标注为估算，且不得作为动作建议的依据** |

**⚠ 这是第二次犯**（第一次 2026-08-03 VRT，当时已定「止盈决策必须以平台实价为准」）。
**规则本身没问题，问题是执行时把估算当了决策依据。下次给动作建议前先问一句：这个数字是平台来的还是我算的？**

### 1.1h 触发条件里必须至少有一条是「单标的级」的（2026-08-21 由 INTC/HOOD 反向移动暴露）

**事故形态**：8/19 为持仓设定的五条触发条件中，最硬的一条是「组合浮亏达 −$500 → 无条件减仓」。
8/21 HOOD 单日 +13.35%、INTC −2.19%，**组合浮亏由 −$355「改善」到 −$73**——
但分开看：**INTC 从 −$286 恶化到 −$354，HOOD 从 −$69 改善到 +$281。**

**若一涨一跌持续，组合级触发线可能永远不触发，而恶化的那一笔会一路走到行权价。**

**规则**：
| 层级 | 度量什么 | 必须有 |
|---|---|---|
| 组合级（浮亏、保证金占比、组合 Delta） | 账户总体承受力 | ✓ |
| **单标的级（标的价格线、单笔浮亏、单笔接货占比）** | **风险集中处** | **✓ 不可省** |

**→ 任何一组触发条件，必须至少有一条锚定在单个标的的价格上。
组合级条件度量的是平均，而风险是集中的——平均值可以被一笔盈利掩盖。**

**这是 2026-08-06「R1/R2 度量纪律生效时的损失，R3/R5/R6 度量纪律来不及生效时的损失」的同源问题：
组合级触发属于前者，但真正会打死账户的是后者。**

### 1.1i 下跌会消耗不确定性，不会制造它——附标的 IV 锚表（2026-08-24 第三次犯后定位）

**1.1g 说「不得拿历史波动当未来波动」。三次实证后，可以说得更精确：**

| 日期 | INTC 标的价 | 我用的 IV | **平台反解真实 IV** | 我的偏差 |
|---|---|---|---|---|
| 2026-08-19 | $93.58 | 78% | **63.4%** | 估值高 44% |
| 2026-08-24 | $87.26 | 76% | **59.1%** | 估值高 36% |

**标的从 $93.58 跌到 $87.26（−6.8%），真实 IV 却从 63.4% 降到 59.1%。**

> **我一直在把「已实现的下跌」当作「未来波动会更大」的证据。
> 市场的看法相反：下跌本身在消耗不确定性——坏消息出完了，隐含波动率就往下走。
> 只有「意外」才制造 IV，「下跌」不制造。**

**这个错误有方向性：它总是让我高估已有空头 put 的浮亏，从而夸大减仓的紧迫性。**
2026-08-24 因此连续两天用夸大的数字推动一个减仓决策（称「系统止损只差 1.8%」，
实际 6.3%）。**估值错误若有系统性方向，它就不是噪音，是偏见。**

#### 标的 IV 锚表（由平台实价反解，直接取用，不再每次猜）
| 标的 | IV 锚 | 反解日期 | 备注 |
|---|---|---|---|
| INTC | **60%** | 2026-08-19 / 08-24 | 两次分别 63.4% / 59.1%，取中值 |
| HOOD | **64%** | 2026-08-24 | 8/19 为 61.8%，8/24 为 64.4% |

**用法**：无平台实价时按此表估算，且**只用于方向判断**；
任何动作建议仍须以平台实价为准（1.1g）。新标的首次成交后立即反解并补进本表。

#### 配套自查（每次给动作建议前问三句）
1. 这个数字是平台来的还是我算的？
2. 我用的 IV 有没有因为「今天跌了」而被我上调？
3. 我的估值误差如果有方向，它在往哪边推我的建议？

### 1.1j 用门店数推客流前必须拆自营/加盟；指标名不能跨公司搬（2026-08-25 海底捞记分暴露）

**事故**：8/21 智库文章给出五个可检验预测，8/25 中报实测 **3 对 2 错**。

**错误一（方向错）**：预测客流 **+2%~+5%**，实际 **−3.1%**。
根因：我用「门店数持续净增」当客流增量的依据。但 2026 H1 **自营 1,322 → 1,290（净减 32）**，净增的全是**加盟 41 → 99**，而**加盟店销售额不并入收入**，只贡献特许权使用费。
→ **规则：任何用门店数/网点数推算收入或客流的推理，第一步必须先拆自营与加盟（或直营与代理）。两者在收入口径上不是一回事，混在一起会把方向算反。**

**错误二（更严重，指标名跨公司搬运）**：我在海底捞检验清单第 2 项写「**客户管理收入 CMR**」，还标为「唯一重点看的数字」。CMR 是**阿里巴巴的电商变现指标**，海底捞从不披露。
→ **规则：写检验清单时，每个指标名必须能指回「这家公司哪份文件的哪一栏」。指不回去 = 这个指标不属于这家公司。** 海底捞的对应物是**同店销售额 + 人均消费**。
→ 讽刺之处：那两个数（−1.3% / −0.9%）恰好给出了我想要的答案。**我的分析框架是对的，是标签贴错了。这类错误不影响结论、只影响可信度，因此最容易蒙混过去——必须显式记分才抓得到。**

**元教训**：这两个错都不是「数据没查到」，是**推理链里一个没被审视的中间假设**（门店=客流基数、指标名可迁移）。**预测必须写成可对照的门槛数字，事后必须逐条记分——不记分就学不到。**

### 1.1k ⭐ IV 锚是「某个 moneyness 上的读数」，不是常数——波动率微笑（2026-08-25 平台对账发现）

**事故**：HOOD 82P 我估 $0.34，平台实价 **$0.49，低估 31%**。同日 INTC 85P 我估 $3.91，实价 $3.80，**只偏 +2.9%**。
同一套方法、同一天，一个准一个离谱。差别在 **moneyness**：

| | OTM 程度 | 我用的锚 | 反解真实 IV | 偏差 |
|---|---|---|---|---|
| INTC 85P | **3.0%**（近平值） | 59.1% | **57.7%** | +2.9% ✓ |
| HOOD 82P | **26.8%**（深度价外） | 64.4% | **69.3%** | −31% ✗ |

**HOOD 自身的微笑**：8/24 OTM 20.9% → IV 64.3%；8/25 OTM 26.8% → IV **69.3%**。**越价外，IV 越高，+4.9pct。**

**根因**：我 8/24 从平台价反解出 IV=64.4% 并把它记成「HOOD 的 IV 锚」。
**但那个数是「HOOD 在 20.9% 价外处的 IV」。标的涨了 7.6% 之后 moneyness 变成 26.8%，锚就不再适用了，而我照旧用。**

**→ 规则：IV 锚必须连同 moneyness 一起记，写成「IV@OTM%」。**
- 标的移动使 OTM 变化 **>5pct** 时，锚作废，必须重新从平台价反解。
- 粗略修正（深度价外 put）：**OTM 每多 5pct，IV 加约 4–5pct。**
- 已更新的锚：**INTC 57.7%@OTM3%（9/18）｜HOOD 69.3%@OTM27%（9/25）**

**⚠ 注意这个错的方向与 1.1i 相反。** 1.1i 是「把下跌当作 IV 会上升」→ 系统性**高估**。
本次是「忽略微笑」→ 对深度价外仓位系统性**低估**。
**两条合起来的真正教训不是「我总是高估」或「总是低估」，而是：我一直在用一个缺维度的 IV 模型（只有时间，没有 moneyness）。**
**对卖方的实际影响：低估深度价外 put 的价值 = 高估自己的利润进度 = 可能过早认为「已达标」。今天我就说了 HOOD「82.9% 进度」，实际 75.5%。**

### 1.1l ⚠ 不要把「我建议挂的单」写成「已经挂着的单」（2026-08-25 平台截图暴露）

平台「**今日订单 (0)**」——**HOOD $0.50 限价单从来没有存在过。**
而我在 8/24 与 8/25 的两份扫描里连续写「HOOD 继续挂 $0.50 限价，不主动追价」「挂单大概率已成交」，**措辞完全像是在描述一张在场的订单。**

**→ 规则：凡涉及订单状态，只有两种合法表述：**
1. **「建议下单：<方向> <标的> <价格> <数量>」**（未确认存在）
2. **「平台已确认在场：...」**（用户截图或明示后才能这样写）
**绝不允许出现「继续挂」「维持挂单」这类默认它存在的动词。** 一张不存在的单，会让我把「需要用户执行的动作」误报成「已经在自动运行的机制」——**今天 HOOD 到 $0.49 却没成交，就是这个错的直接代价。**

### 1.1m ⭐ R4 别自己算保证金——读平台的「可取现金 / 净资产」（2026-08-25 定）

**事故**：为了判断能不能加一笔 $160 的小仓，我先后算出四个「保证金占用」，**互相打架，跨度 62%**：
| 推法 | 结果 |
|---|---|
| Reg-T 公式（我一直用的） | $4,626 |
| 风控等级 54.42% × 净资产 | $5,375 |
| 净资产 − 可取现金 | $6,636 |
| 现金余额 − 可取现金 | $7,484 |

**而平台早就把答案摆在那儿了：可取现金 $3,242.02、冻结资金 $0.00、风控等级 54.42%「安全」。**
券商的保证金公式已经作用在「可取现金」这个数上了——**我要的是结论，却去反推它的中间量，还反推错了。**

**→ 规则：R4 改为读平台可观测量，不再自算。**
```
自由资金率 = 可取现金 / 净资产      绿 >30% ｜ 黄 15–30% ｜ 红 <15%
```
**理由：这个数是券商用它自己的真实规则算的，不需要我猜它的公式；且它随价格自动更新。**
自算的 Reg-T 保证金**只保留一个用途：估算「开某笔新仓会占多少」的增量**，不用于判定合规。

**⚠ 但 R5（接货成本/净值）不能这样替代。** 接货是行权后的义务，与保证金无关，**必须继续自己算**：
`接货 = 行权价 × 100 × 张数`。今日 INTC $17,000 = **172%**，超 150% 上限，**这一条平台不会替我看**。

**元教训：先问「平台有没有直接给这个数」，再决定要不要自己算。我这次是反过来的。**

### 1.1n ⭐⭐ 「把会变的东西写成常量」——同一个错，我在同一个仓库犯了四次（2026-09-01 全仓审计）

审计标准我定的是「**能不能静默产出错误结论**」，不是代码整洁度。按这个标准查出四个 P0，
**其中三个是同一类**：

| 位置 | 写死了什么 | 后果 |
|---|---|---|
| `burry_screener.py` | `INSTANT_PERIODS = ["CY2026Q2I"…]` | 跨年后期间全过期，frames 返回空，缺失率飙升，**不报错** |
| `burry_screener.py` | `YEAR = 2025` | 同上，越扫越旧的财年 |
| `ses_universe.py` | `YEARS = range(2019, 2026)` | 新财年永远扫不到，趋势序列停在旧终点 |
| （2026-08-26） | NVDA「Q3 指引 >$1,060亿 = 加速」 | 基数从估计的 921.6 变成实际 962，阈值静默失效，把「维持」判成「加速」 |

**⭐ 这类错误最危险的地方：写死值在写下的那一刻是完全正确的，所以没有任何信号提示它会坏。**
实测：2026-09-01 当天，推导值与写死值一字不差；到 2027-03-01 全部过期，而脚本依旧安静运行。

**→ 硬规则：任何「期间、年份、基数、当前状态」都必须从运行时推导或从数据源发现，不得写成常量。**
**→ 唯一例外：制度事实**（如 13F 单位切换日 2023-01-03 是 SEC 规则变更日）——它不随时间改变。
**→ 自查一句：这个常量在一年后还对吗？如果答案取决于「今天是哪天」，它就不能是常量。**

### 1.1o 给一族指标设统一阈值前，先看各自的波动量级（2026-09-01）

`tail-risk-monitor` 的加速度条款写「任一指标单日变化 >10% → 上调一级」，
我据此两次（8/24、8/31）用 VIX9D 把绿灯判成黄灯。**实测：**

| 指标 | 平均日变动 | 超 10% 触发率 |
|---|---|---|
| **VIX9D** | **6.44%** | **3/9 = 33%** |
| VIX | 2.42% | 0/8 |
| SKEW | 1.23% | 0/7 |
| VVIX | 2.80% | 0/7 |

**VIX9D 的波动是 SKEW 的 5.2 倍。同一个门槛套上去，触发率 33%——那不是警报，是噪音。**
且 VIX9D 在计分体系里没有区间、没有得分——**对不在规则定义域内的量执行「上调一级」，是越界。**

**→ 规则：给一族指标设统一阈值前，先看它们各自的日波动量级。差 5 倍以上就不能共用门槛。**
**→ 追认：8/24 与 8/31 两次黄灯均为误判。方向是「假黄灯」（过度保守），
   但这不是不修的理由——反复假警报会让灯色失去意义，下次真该黄灯时它已经不值钱了。**

### 1.1p 代理必然有误差，关键是误差方向可控且被承认（2026-09-01）

本轮三处「用代理量替代真实量」，全部出现误伤，且**误伤方向由代理的业务含义决定，不是随机的**：

1. `FINANCIAL_FINGERPRINT` 单标签判行业 → U-Haul（卡车租赁）、ADM（粮商）、VALHI（化工）被判金融。
   **改为带规模检验的三类判别后，判金融从 645 家降到 252 家。**
2. 修第一版时 CNA 财险判漏，直觉是调低投资收益阈值——**那是凑答案**。
   真正的判别式是**准备金的期限**：财险 1.85×营收（长尾浮存金）vs MCO 0.08×（一个月，本质应付账款）。
   **差 20 倍，用 1.0× 切开稳健得多。阈值该不该调，看的是判别式对不对，不是结果好不好看。**
3. 我自己写的审计脚本首跑就误报（把 `ses_screener.py` 的事实筛选 continue 判成静默丢弃）。
   **修检测器而非改代码——会喊狼来了的检测器最终会被忽略，宁可漏报也不要习惯性误报。**

**→ 一条可推广的：任何「用一个可观测量代理一个概念」的设计，
   都要先问「这个代理会把什么误判进来」，并让误伤方向是可承受的那一侧。**

### 1.1q 客户问卷填表：数据在披露体系中"结构性不存在"时，正确交付是「未披露」而不是推算值（2026-09-02，绿茶AI支出调研表）
- 场景：客户要绿茶(6831.HK)集团层面 IT预算/AI预算/AI实际支出/场景占比/外采占比，并明确"表格中不要出现推测等不确定术语"。六项中四项港交所餐饮企业**根本不作独立财务列报**（分散在行政开支/其他开支/物业厂房设备），同业海底捞/九毛九同样不披露。
- **规则**：区分"检索未尽"与"结构性缺失"。前者要继续查；后者要**论证它为什么取不到**（科目体系＋同业对照），给侧向代理数据（本次＝招股书IT专项 HK$4,030万、AI场景清单、厂商名），再把空白转成访谈提问清单。**"未披露"是对披露状态的事实陈述，可核查可追责；填推算值会让表格看起来完整、实则不可用。**
- **不填推算的量化理由要写出来**：餐饮IT费率同业离散度极大＋绿茶门店年增46%属扩张期，费率基准不可迁移，**误差量级超过被估计值本身**。没有这句，"不填"看起来像偷懒。
- ⚠ 与 Critic D3「数据缺口须有推测替代」的关系：D3 有明文豁免——"结构性缺失且已给出侧向代理数据"。**客户显式禁止推测时，D3 让位于客户口径，但必须在分析师附注里声明这次为什么不走推测路径。**

### 1.1r 填客户问卷先核对「问卷时点 vs 事件时点」（2026-09-02，同上）
- 问卷问"截至2026年6月底的AI实际支出"，而绿茶首个AI合作（蚂蚁数科）签于 **2026-07-24，晚于截止日**。若不查时点，容易把7月之后的合作信息填进6月底的栏里，凭空造出一笔不存在的期内支出。
- **规则：任何"截至X日"的栏位，先把已知事件按日期排序，明确哪些落在窗口外。时点错位本身往往就是该栏最有信息量的答案**，比填一个数更有价值。

### 1.1s 分部加总≠总额时，必须在交付物里显式说明差额（2026-09-02，同上）
- 绿茶2026H1：堂食20.14亿＋外卖6.51亿＝26.65亿，总额26.75亿，差0.10亿(0.4%)。我初稿两个数都列了却没说差额——**客户自己一加就会认为表格自相矛盾**，且这正是 Critic D2 的硬触发条件。
- **规则：凡同表并列"总额＋分项"，自己先加一遍。加不平就写明差额去向（或写明"余额为本表未列示项"），不要留给读者去发现。**

### 1.1t ⭐ R5/R4 是提示项，不是否决项（2026-09-03 用户第二次纠正）
- **用户原话**：「R5你只需要提示我就可以，不要作为不开仓的理由」
- **这是第二次说**。此前 2026-08 已说过「仓位的问题你负责提醒，但不要被仓位束缚手脚，该怎么找机会就继续」，我执行一段时间后又退回成「R5 超限 → 无新仓」的硬否决，连续多个扫描日用它当结论。
- **规则**：
  1. **R4/R5/R3 一律降级为「提示」**——在报告里给出数字和超限幅度，**然后继续给出完整的机会清单与可执行方案**。
  2. **禁止**把仓位规则写成「不开仓」的裁定理由。裁定只能基于**尾部灯色 + 标的质量 + 赔率**。
  3. 红灯仍是硬否决（tail-risk skill 铁律 2），**这一条不变**——灯色和仓位规则是两回事，别混。
  4. 账户是用户的，**仓位上限由他自己权衡**；我的职责是把风险量化摆出来，不是替他决定不做。
- **教训（比规则本身更重要）**：用户纠正过的行为，我会在几周后无声地退回原状。**"我说过一次"不等于"它被固化了"——凡用户纠正过的执行偏好，必须当场写进 profile，不能只在当次会话里遵守。**
